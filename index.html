Rakali

Rakali is a GPU-native Fortran solver for coastal, estuarine, and tidal applications. It supports structured Cartesian grids (2D barotropic, 3D hydrostatic multilayer, non-hydrostatic) and unstructured triangular grids (2D barotropic, 3D hydrostatic multilayer with KNP central-upwind).

GPU parallelism is expressed with do concurrent + OpenACC, portable across NVHPC (GPU and multicore), gfortran, and ifx.

Two grid backends

  • Structured (Cartesian): HLL/HLLC + hydrostatic reconstruction, A-grid.
  • Unstructured (triangular): KNP central-upwind, Green-Gauss gradients.

The full architectural overview, repository map, and run lifecycle live in docs/codebase/INDEX.md. The design contract is in src/core/coastal/README.md.

Building

module load cmake nvhpc
cmake -B build -S .
cmake --build build
cd build && ctest --output-on-failure

Key CMake options:

Option Default Description
RAKALI_ENABLE_GPU ON OpenACC GPU offload via NVHPC
RAKALI_ENABLE_PYTHON OFF Build the librakali.so Python/Julia FFI
RAKALI_GPU_ARCH cc70 Target GPU compute capability (cc70/80/90)
RAKALI_ENABLE_DOUBLE ON Double-precision working precision

The full list lives in CMakeLists.txt.

Do not pass -j N to ctest when the GPU build is active — every worker shares one GPU, so parallel test execution produces spurious failures and hangs. Building with -j is fine; only ctest -j N is the problem. Use ctest -R rakali for the ~164-test rakali-only subset (~60 s) for fast regression checks.

Documentation

Per-module and per-procedure documentation is generated by FORD from !! docstrings in the source — that is the canonical reference. Hand-maintained synthesis documents complement it:

  • docs/CLOSURE_MATRIX.md — which closure/scheme is active on which path, plus tunable knobs (drift-checked by tools/check_closure_matrix.py).
  • docs/CAPABILITIES_AND_LIMITATIONS.md — what is shipped, what is deferred.
  • docs/REFERENCE.md — physics + namelist reference.
  • FORTRAN_STYLE.md — coding style and the do concurrent + OpenACC GPU programming model.
  • docs/codebase/CONCEPTS.md — glossary of acronyms.
  • docs/codebase/INDEX.md — repository map and run lifecycle.

Comments prefixed with !! are documentation comments processed by FORD. Comments prefixed with a single ! are ordinary code comments and are not rendered. Please do not use !! for casual code comments.

Dependencies

  • Fortran compiler — NVHPC (GPU + multicore), gfortran, or ifx.
  • CMake ≥ 3.22.
  • NetCDF-Fortran.
  • Internet access at configure time to pull pic and test-drive.

Pre-commit workflow

Before each commit, in order:

  1. pre-commit run --all — formatting (whitespace, trailing newlines, end-of-file).
  2. fortitude check — Fortran static checks (also wired up as a pre-commit hook).
  3. ctest — full test suite. Never pass -j N on the GPU build.
  4. Re-read the synthesis docs (CLOSURE_MATRIX.md, the design-contract READMEs, docs/howto/, CAPABILITIES_AND_LIMITATIONS.md) and update anything that drifted. When code and docs disagree, the code is authoritative.

When adding a new capability: namelist knob (default off, preserves bit-identity) → kernel gated on the knob → unit test (analytical tests are high-leverage) → format/lint/test → one commit per capability, one PR per capability.
